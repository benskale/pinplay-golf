PinPlay — Flexible Game Config

Design Doc · Updated 2026-07-17 · Open questions resolved

What We're Building

A flexible game-config system that lets PinPlay handle any golf format — from a casual 2-player match to a 4-day, 20-player tournament with multiple bet pools, rotating partners, and custom scoring rules — without hardcoding every format as a separate game type.

Two entry paths into the same config:

  1. Presets (dropdowns) — fast path, covers common formats that already exist
  2. Custom Game (LLM-powered) — describe your format in plain language, app parses it into a valid config
Key rule: Config is frozen once the round/tournament starts. Side bets can still be added mid-round (they slot into the bet pool system, not the game config).

Config Schema

Every game — preset or custom — produces the same JSON shape. The scoring engine reads this config and knows exactly what to do. Presets are just pre-built configs; the LLM generates configs in the same shape.

GameConfig (per day / per round)

interface GameConfig {
  // ── Identity ──
  id: string;                          // "custom_xxx" or preset id
  name: string;                        // display name
  source: "preset" | "custom";         // how it was created

  // ── Players & Teams ──
  playerCount: number;
  teamStructure: TeamStructure;

  // ── Scoring ──
  scoring: ScoringRules;

  // ── Bet Pools ──
  betPools: BetPool[];

  // ── Press Rules ──
  pressRules?: PressRules;

  // ── Mini-Games (auto-tracked) ──
  miniGames: MiniGameConfig[];

  // ── Side Bets (1-on-1 personal wagers) ──
  sideBets: SideBetConfig[];

  // ── Metadata ──
  needsHandicap: boolean;
  carryover: boolean;
  specialInputs?: string[];            // e.g. ["bingo","bango","bongo"]

  // ── Template / Sharing ──
  isTemplate?: boolean;                 // saved as shareable template
  templateId?: string;                // ID if created from a shared template
  authorName?: string;
  description?: string;               // human-readable summary
  tags?: string[];                     // ["wolf", "high-stakes", "beginner"]
}

interface Player {
  id: string;
  name: string;
  handicapIndex?: number;
  handicapSource: "ghin" | "manual" | "none";
  ghinNumber?: string;
  teamId?: string;
}

interface GameTemplate {
  id: string;
  config: GameConfig;                  // frozen config snapshot
  name: string;
  authorName: string;
  description: string;
  tags: string[];
  uses: number;                        // popularity counter
  rating?: number;                     // optional community rating
  createdAt: string;
}

TeamStructure

interface TeamStructure {
  type: "individual" | "teams";
  teams?: TeamDef[];
  assignmentMode?: "preset" | "rotating" | "wolf_style";
  rotationRules?: RotationRules;
}

interface TeamDef {
  id: string;        // "A", "B", "C"...
  name: string;
  playerIds: string[];
}

interface RotationRules {
  method: "segments" | "per_hole" | "wolf_pick";
  segments?: number;          // e.g. 3 segments of 6 holes
  wolfOrder?: "last" | "first";
}

ScoringRules (the heart of the system)

interface ScoringRules {
  format: ScoringFormat;
  // stroke_play | match_play | skins | points | stableford | quota

  countingScores?: CountingScoreDef[];
  // e.g. "2 best gross + 1 best net" = [
  //   { type: "gross", count: 2, order: "low" },
  //   { type: "net",  count: 1, order: "low" }
  // ]

  pointsTable?: Record<string, number>;
  // e.g. { eagle: 4, birdie: 2, par: 1, bogey: 0 }

  stablefordTable?: Record<string, number>;

  carryover: boolean;
  carryoverType?: "skins" | "nassau";

  handicapBased: boolean;
  handicapMethod?: "full" | "match_play_diff" | "peoria" | "callaway";

  holeValue?: number;        // e.g. $5 per hole
  holeValueUnit?: "points" | "dollars";

  segments?: ScoringSegment[];
  // Nassau = front 9, back 9, overall
}

interface CountingScoreDef {
  type: "gross" | "net";
  count: number;
  order: "low" | "high";
}

type ScoringFormat =
  | "stroke_play"
  | "match_play"
  | "skins"
  | "points"
  | "stableford"
  | "quota"
  | "nine_point"
  | "bingo_bango_bongo"
  | "custom";

BetPool

interface BetPool {
  id: string;
  name: string;          // "Team Match", "Skins", "Closest to Pin"
  type: BetPoolType;
  scope: "per_hole" | "per_round" | "per_day" | "per_tournament";
  participants: "all" | "teams" | "individuals" | string[];
  value: number;
  valueUnit: "per_hole" | "per_round" | "per_point" | "flat";
  qualifier?: string;      // "par 3s only", "birdies only"
}

type BetPoolType =
  | "match" | "skins" | "pool"
  | "achievement" | "side_bet" | "custom";

PressRules

interface PressRules {
  enabled: boolean;
  maxPerHole: number;         // 3 default
  multiplier: number[];       // [2, 4, 8]
  whoCanPress: "anyone" | "losing_only";
  responseType: "accept_or_drop";
  crossGroup?: boolean;       // press between teams in tournament
}

TournamentConfig

interface TournamentConfig {
  id: string;
  name: string;
  totalDays: number;
  players: Player[];
  teams?: TeamDef[];

  days: TournamentDay[];          // per-day game configs
  tournamentPools: BetPool[][];    // span all days

  leaderboard: LeaderboardConfig;
}

interface TournamentDay {
  dayNumber: number;
  gameConfig: GameConfig;       // preset or custom per day
  status: "upcoming" | "in_progress" | "complete" | "rest_day";
}

interface LeaderboardConfig {
  aggregation: "total_strokes" | "total_points" | "match_record" | "custom";
  countingMethod?: CountingScoreDef[];
  tiesResolvedBy?: "playoff" | "countback" | "split";
}

GLM Prompt Design

  • System prompt gives GLM the full GameConfig schema
  • 10-15 few-shot examples (natural language to config mappings)
  • Golf terminology glossary (skins, nassau, press, shamble, etc.)
  • Strict instruction: output ONLY valid JSON, no explanation
No LLM during live scoring. The LLM runs ONCE at setup time. After that, the config is frozen and the scoring engine (pure TypeScript, deterministic) handles everything. Live scoring stays fast and reliable.

Scoring Engine

The current game-logic.ts uses a giant switch statement on gameType string. The new engine replaces this with a config-driven approach:

// Instead of:
switch (gameType) {
  case "match_play": ...
  case "skins": ...
}

// New approach:
function scoreHole(config: GameConfig, holeData: HoleData): HoleResult {
  // 1. Apply handicap strokes if config.scoring.handicapBased
  // 2. Compute counting scores per config.scoring.countingScores
  // 3. Compare per config.scoring.format
  // 4. Update bet pools per config.betPools
  // 5. Handle press per config.pressRules
  // 6. Return structured result
}

Existing presets still work because they produce GameConfig objects. The switch statement gets replaced incrementally — each preset's logic moves into a config-driven function.

Handicap Lookup (GHIN)

GHIN (Golf Handicap and Information Network) is the USGA's handicap system used by most US golfers. Looking up handicaps automatically removes friction from tournament setup — especially for 20+ player events.

How It Works

  • Organizer enters a player's GHIN number (or last name + club)
  • PinPlay queries GHIN's handicap API for the player's current Handicap Index
  • Index auto-fills into the player record
  • Strokes per hole auto-calculated from course slope/rating using the World Handicap System formula
GHIN API access: The GHIN handicap lookup is available through the public GHIN website and mobile app. PinPlay can use the same lookup endpoint (ghin.com search). For batch tournament entry, the organizer can paste a list of GHIN numbers and PinPlay looks them all up in parallel.

Fallback Chain

  1. GHIN lookup — best case, accurate and current
  2. Manual entry — organizer types handicap index directly
  3. No handicap — player plays scratch (0 strokes), used for casual rounds or no-handicap events

Each player record stores the source (handicapSource: "ghin" | "manual" | "none") so the scoring engine knows the provenance.

Config Sharing & Game Templates

Custom game configs can be saved as reusable templates and shared with other PinPlay users. This turns one person's creative game format into something the whole community can try.

How It Works

  • After creating a custom game (via LLM or manual config), user sees a "Save as Template" option
  • Template captures the frozen GameConfig snapshot plus a name, description, and tags
  • Saved templates appear in a Community Games browser, sortable by popularity, tags, or recency
  • Other users can one-tap load a template, adjust player count / stakes to their group, and start

Template Browser

Create Custom Game → Save as Template → Community Games Browser │ ┌─────────────────────────────────┤ │ │ Trending Browse by Tag (most used this month) (wolf, skins, team, high-stakes, beginner...) Load Template → Adjust Players/Stakes → Start Round
Viral potential: A clever game format can spread through golf groups organically. "We played this wild format we found on PinPlay" becomes user acquisition. Templates are shareable via link (pinplay.golf/game/abc123) — tapping the link opens PinPlay pre-loaded with that config.

Template Lifecycle

  • Template stores a snapshot of the config at save time — it doesn't update if the original game is edited later
  • Loaders can modify player count, stake amounts, and team assignments — the scoring rules stay as the author intended
  • Template use count increments each time someone starts a game from it
  • Author can delete their own templates at any time

Offline / Local-First Mode

Many golf courses have poor or no cell service. PinPlay's current architecture relies on WebSocket for real-time multiplayer sync. For tournaments and group games, losing connection mid-round is unacceptable — scoring must continue uninterrupted.

Architecture: Local-First with Sync Queue

┌─────────────┐ Score Input ───→ │ Local Store │ ← always writes here first │ (IndexedDB) │ └──────┬───────┘ │ ┌────┴────┐ │ Sync │ │ Engine │ └────┬────┘ │ ┌───────────┴───────────┐ │ │ Online Offline │ │ Push to server Queue locally via WebSocket (every score stored) │ │ Other players When connection see updates returns, flush in real-time entire queue to server in order

Key Design Decisions

  • Every score writes to local IndexedDB first — this is the source of truth during play, not the server
  • Sync engine runs as background process — pushes to server when connected, queues when not
  • Queue is ordered — scores replay in the exact order they were entered, preventing state corruption
  • Conflict resolution: last-write-wins per hole — if two devices scored the same hole differently while offline, the latest timestamp wins and the other device gets a notification
  • Tournament organizer's device is authoritative — in offline mode, the organizer's phone is the master scorecard; other players' devices sync to it when reconnected

Offline Capabilities

  • Full scoring (all game types, all bet pools, all calculations)
  • Leaderboard updates (local only until reconnected)
  • Settlement card generation
  • Course data and pars (pre-cached at round start)
  • Game config (frozen at start, always available locally)

What Does NOT Work Offline

  • Real-time sync to other players' devices
  • GHIN handicap lookup (do this before the round)
  • Custom game LLM parsing (do this before the round)
  • Loading new templates from the community browser
Pre-round caching: When a round or tournament starts, PinPlay caches the entire game state — config, course data, player list, par/handicap tables — to IndexedDB. This happens automatically and silently. The app is always ready to go offline.

Decisions Log

  1. Max player count for regular rounds? → Any number, with a soft nudge. No hard cap. At 6+ players, prompt: "Want to set this up as a group game?" Routes to tournament flow if yes, continues as regular round if no.
  2. Handicap sources? → GHIN lookup first, manual fallback. Per-player GHIN number lookup (single or batch). Manual entry for players without GHIN. Source tracked per player record.
  3. Config sharing? → Yes, full template system. Save custom configs as shareable templates. Community browser with trending, tags, search. Shareable via link. Viral growth mechanism.
  4. Offline handling? → Local-first mode. Every score writes to IndexedDB first. Sync engine pushes to server when online, queues when offline. Organizer's device is authoritative during offline tournaments. Pre-round caching makes the app always ready to go offline.
